# TaskFlow

A simple to-do list web app built with plain HTML, CSS and JavaScript. Tasks are stored in Cloud Firestore, so they persist after a page refresh and are available on any device.

**Live demo:** PASTE_YOUR_GITHUB_PAGES_LINK_HERE
**Repository:** PASTE_YOUR_REPO_LINK_HERE

## Features

- Add a task (press Enter or click Add). Empty or whitespace-only tasks are rejected with a visible message.
- Tasks load from Firestore on page load, newest first.
- Mark a task as complete with its checkbox (shown with a strikethrough).
- Edit a task title with the Edit button. Press Enter or Save to confirm, Escape or Cancel to discard.
- Delete a task, with a confirmation prompt.
- Filter by All, Active or Completed. The active filter is highlighted.
- "Tasks left" counter.
- Loading state while fetching, and friendly error messages if a database request fails.
- Responsive layout that works from 360px wide up to desktop.
- Accessibility: semantic HTML, labelled inputs, descriptive `aria-label`s on buttons, visible focus outlines and full keyboard support.

## Tech stack

- HTML5 and CSS3 (custom properties, Flexbox, mobile-first media query)
- JavaScript (ES modules, async/await, event delegation)
- Cloud Firestore (Firebase JS SDK v10.12.2, loaded from the CDN)
- No frameworks or CSS libraries

## How it works

- `tasks` is an array that acts as the single source of truth for the screen. After every change, `renderTasks()` redraws the list from it.
- Each database action (add, complete, edit, delete) waits for Firestore to succeed before updating the array, so the screen never shows something that was not saved.
- A single click listener on the list uses event delegation, and each task's Firestore ID is stored in a `data-id` attribute.
- A shared `runAction()` helper wraps every database call in `try/catch`, shows a friendly error message and redraws.
- User-typed text is inserted with `textContent`, never `innerHTML`, to avoid HTML injection.

## Data model

Each task is one document in the `tasks` collection:

| Field       | Type      | Notes                                 |
|-------------|-----------|---------------------------------------|
| `title`     | string    | 1 to 100 characters                   |
| `completed` | boolean   | defaults to `false`                   |
| `createdAt` | timestamp | `serverTimestamp()`, used for sorting |

The document ID is generated by Firestore.

## Firestore security rules

The database is not in test mode. These rules validate the shape of every task that is created or updated, and block access to any other collection:

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    function isValidTask(data) {
      return data.keys().hasOnly(['title', 'completed', 'createdAt'])
        && data.title is string
        && data.title.size() >= 1
        && data.title.size() <= 100
        && data.completed is bool
        && data.createdAt is timestamp;
    }

    match /tasks/{taskId} {
      allow read: if true;
      allow create: if isValidTask(request.resource.data);
      allow update: if isValidTask(request.resource.data);
      allow delete: if true;
    }
  }
}
```

The Firebase web `apiKey` is not a secret. Access to the data is controlled by these rules. Because there are no user accounts, anyone with the link can read and delete tasks. Per-user rules would need Firebase Authentication (see below).

## What I learned

Building TaskFlow in stages taught me the value of getting the logic working with a plain JavaScript array first, then swapping in Firestore. Debugging the interface and the database separately was much easier than doing both at once.

I learned how event delegation works: one listener on the list can handle every checkbox and button by reading `event.target` and the `data-id` of the closest task, which keeps working when the list is redrawn.

I also practised async/await with `try/catch/finally` for loading and error states, and learned to update the screen only after Firestore confirms a change. Setting up Firestore showed me how security rules work: a database created in production mode blocks everything, and I wrote rules that validate the shape of each task instead of leaving it open in test mode.

On the front end, I used semantic HTML, `aria` attributes, a visually hidden label and focus outlines so the app works with a keyboard and screen readers, and a mobile-first layout that holds up at 360px.
